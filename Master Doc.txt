09. Stock

El sistema deberá mantener control de inventario para cada producto o variante.

Conceptualmente:

Stock disponible
Stock reservado
Stock total

El stock deberá controlarse del lado del servidor, evitando depender exclusivamente del frontend.

El sistema deberá impedir que se confirme una compra cuando no exista stock suficiente.

Cuando un pedido sea creado, el sistema deberá contemplar la reserva/descuento correspondiente del inventario.

El administrador podrá:

consultar stock
modificar stock
agregar unidades
descontar unidades
visualizar productos agotados

A futuro se podrá incorporar un historial de movimientos de inventario.

10. Carrito

Los clientes podrán:

agregar productos
seleccionar variantes
modificar cantidades
eliminar productos
consultar subtotal
consultar costo de envío
consultar total

El carrito podrá ser utilizado sin autenticación.

Sin embargo:

No se podrá finalizar una compra sin autenticarse.

Para usuarios no autenticados, el carrito podrá almacenarse localmente.

Para usuarios autenticados, el carrito podrá sincronizarse con Supabase.

El sistema deberá evitar agregar cantidades superiores al stock disponible.

13. Pagos

El método de pago principal será inicialmente Mercado Pago.

La arquitectura deberá permitir incorporar otros métodos posteriormente.

Flujo conceptual:

Cliente
   ↓
Checkout
   ↓
Crear operación de pago
   ↓
Mercado Pago
   ↓
Cliente realiza el pago
   ↓
Mercado Pago
   ↓
Webhook
   ↓
Edge Function
   ↓
Validación del pago
   ↓
Actualizar pedido
   ↓
Actualizar stock

El sistema no deberá considerar un pedido como pagado únicamente porque el frontend informe que el pago fue exitoso.

La confirmación deberá realizarse mediante comunicación server-side/webhook y validación con Mercado Pago.

15. Panel Administrador

Un usuario común nunca deberá poder acceder a funcionalidades administrativas aunque intente navegar directamente hacia las rutas del dashboard.

registrarse

Checkout

Administración

El dashboard deberá requerir:

Usuario autenticado
        ↓
¿Rol ADMIN?
        │
    ┌───┴───┐
    NO      SÍ
    ↓       ↓
 DENEGAR   ACCESO

La autorización deberá implementarse tanto en:

frontend
Supabase / RLS
Edge Functions cuando corresponda

Nunca confiar únicamente en las protecciones del frontend.

Row Level Security

Supabase deberá utilizar RLS (Row Level Security) para controlar qué datos puede consultar o modificar cada usuario.

Ejemplos:

Cliente

Puede:

VER productos públicos
VER sus propios pedidos

No puede:

MODIFICAR productos
MODIFICAR stock
VER pedidos de otros clientes
MODIFICAR pedidos ajenos
Administrador

Puede administrar los recursos necesarios del sistema.

Toda lógica sensible relacionada con pagos deberá ejecutarse server-side.

Nunca:

Frontend
   ↓
"Pago aprobado"
   ↓
Pedido PAGADO

Mercado Pago
      ↓
Webhook
      ↓

      ↓

Toda información enviada por el usuario deberá validarse.

Ejemplos:

teléfono
dirección
cantidades

18. PERFORMANCE

La regla principal será:

La tienda debe cargar solamente la información necesaria.

No repetiremos el problema actual de:

1.000 productos
       ↓
Frontend descarga los 1.000
       ↓
React filtra

En su lugar:

Usuario busca
       ↓
Supabase
       ↓
devuelve solamente resultados necesarios
Catálogo

Implementaremos:

paginación
filtros server-side
búsqueda server-side
ordenamiento server-side
límites de resultados

Por ejemplo:

Productos 1–24
        ↓
[ Siguiente ]
        ↓
25–48
Imágenes

Las imágenes son uno de los elementos más importantes para un e-commerce.

Deberemos utilizar:

formatos optimizados
compresión
thumbnails
lazy loading
tamaños apropiados
imágenes responsive

No tiene sentido cargar una imagen de 4 MB para mostrarla a 300 × 300 px.

Code splitting

Las secciones que no sean necesarias inmediatamente deberán poder cargarse bajo demanda.

Especialmente:

Tienda
      ↓
carga catálogo

Admin
      ↓
carga dashboard

No queremos que el usuario que solamente está mirando un producto tenga que cargar todo el código del panel administrativo.

Caché

Deberemos aprovechar caching donde tenga sentido:

categorías
productos
imágenes
configuraciones
datos que cambian poco

Pero sin cachear incorrectamente información crítica como:

stock
estado de pago
pedidos
Performance objetivo

No establecería ahora números artificiales imposibles de garantizar, pero sí una regla:

La aplicación deberá mantener una experiencia fluida a medida que aumenten los productos, usuarios y pedidos.

Y se deberán evitar operaciones que crezcan innecesariamente con el tamaño total de la base de datos.
